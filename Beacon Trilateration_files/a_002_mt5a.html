How our trilateration turns four distances into a robot position

Every tag_status message gives the positions of the anchors that answered and the measured distance from the tag to each of them. The code turns that into one (x, y) point in the lab frame. The example numbers below come from a real message in loc_square_right, 13.4 s into the run.

The idea in one picture

A distance to one anchor says the tag lies on a sphere around it. The robot drives on a flat floor, so we fix the tag height at h = 0.3 m and cut each sphere with that horizontal plane. Each anchor then gives a circle on the floor, and the robot is where the circles meet.

Up close the circles never meet exactly

Each distance has a few centimetres of noise, so the four circles don't pass through one point. The algorithm looks for the point whose distances to the four anchors differ least from the measured ones. That is a least-squares problem, and we solve it in two stages.

Step 1 · Project each distance onto the floor

The measured distance ri is a 3D distance. Since the tag height is fixed, we remove the vertical part and get the radius of the circle on the floor:

ρᵢ² = rᵢ² − (h − zᵢ)² h = 0.3 m, zᵢ = 1.6 m → (h − zᵢ)² = 1.69 m²

For anchor 1419 that is √(5.372² − 1.69) = 5.212 m. The vertical part is small because the anchors are several metres away horizontally. That is also why the tag height barely changes the result.

Step 2 · Linear least squares for a starting point

Each anchor gives one circle equation. Subtracting the equation of the first anchor from the others cancels x² and y², and what is left is linear:

(x − xᵢ)² + (y − yᵢ)² = ρᵢ² for every anchor i 2(xᵢ − x₀)·x + 2(yᵢ − y₀)·y = ρ₀² − ρᵢ² + xᵢ² − x₀² + yᵢ² − y₀² A · [x, y]ᵀ = b → solved with numpy.linalg.lstsq

With 4 anchors that is 3 equations for 2 unknowns, solved in the least-squares sense. It needs no starting guess and always returns an answer, here (5.05, 1.89) m. The subtraction mixes the noise of anchor 0 into every equation, so this point is good but not optimal. Its RMS residual is 18.5 cm.

Step 3 · Nonlinear least squares to refine it

Starting from the linear point, scipy.optimize.least_squares moves (x, y) to minimise the real error, which is the difference between the distance to each anchor and the measured one:

minimise Σᵢ ( ‖ aᵢ − (x, y, h) ‖ − rᵢ )²

Every anchor counts equally and nothing is mixed between them. In the example the point moves 12 cm, to (4.99, 1.99) m, and the RMS residual drops to 15.8 cm.

Not every message produces a fix. This is the path one tag_status message takes through BeaconLocalizer and Trilaterator.

Limits to know about

  1. Gaps in the data. The tag sometimes stops measuring for 1–10 s while the robot keeps driving. Our position stays frozen at the last fix, which looks like a delay. This is in the data itself, not in the solver.
  2. Height (z) can't be trusted. All anchors hang at 1.6 m, so z only enters as (z − 1.6)². That gives two mirror solutions and very low sensitivity, which is why z is fixed. A 3D mode exists (--mode 3d) but its z jumps between −1.3 m and 1.55 m.
  3. No time filtering. Each fix uses only its own message. The fixes are a little noisier than tag_pose, but they react immediately. tag_pose appears to be smoothed and lags 0.2–0.5 s behind the wheel odometry.
